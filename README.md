## Problem and data

The model predicts whether an industrial machine will fail within seven days. The input is a
synthetic dataset generated by [`scripts/make_dataset.py`](scripts/make_dataset.py), not an
external download: 240 machines, 25 readings per machine, six sensor features, and the binary
target `failed_within_7d` with a positive rate near 12%.

Machines have persistent characteristics — a hot-running machine reads hot in every row. So the
train/validation/test split is **grouped by `machine_id`**: every reading from one machine lands
in exactly one partition. Splitting row-wise instead lets the model memorise the machine and
reports a validation score that will never survive production. `tests/test_data.py` asserts this
property holds, and Lab 4 turns it into a CI gate.

Bringing your own dataset is allowed. Replace `scripts/make_dataset.py`, update the schema in
`src/data.py`, and keep every test passing.

### data contract tests and the production incidents they would catch

The contract tests in `tests/test_data.py` are not generic "good style" checks; each one is
meant to fail when an upstream producer breaks the data contract in a way that would otherwise
silently poison production.

- `test_schema_columns_present_and_typed` would have caught the incident where a telemetry
  pipeline upgrade renamed `pressure_kpa` to `pressure` and changed its dtype from numeric to
  string, breaking every request payload and causing the model to receive malformed features.
- `test_no_nulls_in_required_columns` would have caught the incident where the sensor gateway
  started dropping `ambient_humidity` values during a network blip, leaving ~18% of rows with
  nulls and causing the serving stack to use default values that skewed risk predictions.
- `test_features_within_plausible_ranges` would have caught the incident where a unit conversion
  bug flipped `temp_c` from Celsius to Fahrenheit for one plant, creating values like 140°C in a
  dataset that should only contain realistic machine temperatures and causing a false spike in
  failure alerts.
- `test_target_is_binary_and_not_degenerate` would have caught the incident where the label job
  defaulted missing `failed_within_7d` values to `0` after a downstream outage, silently making the
  dataset look perfectly healthy while the positive rate collapsed and the model learned the
  wrong target.
- `test_identifier_is_unique` would have caught the incident where a reprocessing job reloaded an
  old batch and duplicated `reading_id` rows, making the same machine readings appear twice and
  inflating the apparent sample size while corrupting every downstream model evaluation.

These are real production failure modes: schema drift, missing upstream fields, unit bugs,
label corruption, and duplicate-event ingestion. The tests are intentionally designed to fail in
those cases instead of letting a broken dataset reach model training or serving.

### Drift threshold and SLOs

For the production drift check, we use a PSI threshold of 0.25. A PSI below 0.10 is normal
sensor noise for a stable machine fleet; a value between 0.10 and 0.25 says the feature
distribution has shifted enough to deserve attention; values at or above 0.25 are treated as
significant drift because they materially change the input mix and can bias the model even when
aggregate accuracy looks healthy. This is a deliberate, justified threshold rather than a copied
library default.

The service SLO is 99.5% successful requests over a rolling 30-day window, and the endpoint
latency target is p95 under 200 ms over a rolling 7-day window. If the error budget is spent,
we freeze deploys, page the on-call engineer, and revert to the last known-good model while
investigating the incident instead of pushing through degraded service.

### Drift alerting and scheduled monitoring

Task 5 uses Google Cloud Scheduler to start a Cloud Run Job every six hours. The job reads its
training reference and latest production-input CSV directly from a private GCS bucket using its
service identity, writes PSI gauges to Cloud Monitoring, and sends an email via SMTP when a
feature reaches PSI 0.25. Deployment files and setup steps are in
[`monitoring/gcp/README.md`](monitoring/gcp/README.md). A PSI below 0.10 is ordinary sensor noise,
0.10-0.25 merits review, and 0.25+ is a material fleet-level shift that can bias the model.

Set the deployment's `email_to` to a mailbox or paging-enabled distribution list monitored by the
on-call team; SMTP credentials are read from Secret Manager, not GitHub Actions or committed files.
Use Cloud Scheduler's **Run now** action for a one-time schedule trigger test. A successful trigger
starts the job; inspect the Cloud Run Job execution logs and the destination inbox to verify
completion and delivery. For a safe synthetic-drift email test without changing the production
snapshot, execute the Cloud Run Job once with argument overrides as documented in
[`monitoring/gcp/README.md`](monitoring/gcp/README.md).

## Model registry promotion

In a real organisation, promotion to staging should require approval from the ML platform owner or
an on-call model-risk reviewer, not the person who trained the candidate. The approver should require
the evaluation-gate result, validation and held-out test metrics, seed or cross-seed variance, cost
estimate, data and code versions, image digest, MLflow run ID, training-job ID, and a successful
reload check from the registry. They should also confirm that the lineage tags are present on the
registered model version and that a rollback candidate exists before assigning the `staging` alias.

## Scheduled retraining policy

For this machine-failure prediction system, the right question is not "how often should we retrain in
principle?" but "what signal tells us the existing model has become stale or misleading in a way that
matters to deployment?" The answer is a hybrid: a weekly schedule is the safety net, and a drift-triggered
retraining check is the operational trigger for real fleet changes.

| Strategy | When it is right for this system | How it fails here |
|---|---|---|
| Fixed schedule | Good as a backup control. A weekly run guarantees we revisit the model even if no one notices drift or new data. | It retrains on time even when nothing has changed, which wastes compute and can create unnecessary churn. It also misses sudden distribution shifts that appear between scheduled runs. |
| Data volume threshold | Reasonable only when new data arrives in predictable batches and data quality is trusted. | This problem is not dominated by raw volume. The important signal is change in sensor distribution, not whether we reached 100 more rows. A volume threshold can retrain after a noisy but harmless batch and can also delay retraining while the fleet is already drifting. |
| Drift-triggered | Best fit for a sensor fleet with stable semantics and known feature drift risk. We care about whether the production distribution shifts materially, not simply whether more rows arrived. | The failure mode is severe: if upstream telemetry is corrupted and the drift check reports a fake shift, retraining on poisoned data can destroy a working model faster than a fixed weekly schedule would. A drift-only policy without validation is therefore unsafe. |

I chose a weekly scheduled pipeline with drift-triggered retraining as the operational trigger. In plain terms:

- the weekly run is the safety net and audit trail;
- the drift check can trigger an earlier retrain when the feature distribution moves materially;
- the model still does not register unless the evaluation gate passes and the data contract tests pass.

The worst case is a corrupted upstream sensor feed: a broken gateway or unit conversion bug can make the
feature distribution appear to drift even though the underlying business signal is still valid. In that case,
a drift-only policy would retrain on bad data and could degrade a healthy model faster than a fixed schedule
would. This is exactly why the pipeline must validate data before training and still require a real gate before
registering or deploying.

## Portability seam write-up

The hardest method to port was `invoke`, because the cloud providers expose almost the same operational idea
(prediction request + response payload) but with different route names, authentication paths, and response
wrappers. A file upload or download is straightforward to map by object URI, but invoking a serving endpoint
always leaks a bit of provider-specific semantics through the seam. The most obvious leak was the prediction
payload itself: the service response is not a neutral JSON document across providers, because the endpoint
wrapping, metadata fields, and inference route conventions differ enough that the adapter must translate them.

A full migration would cost real engineering time — roughly one to two engineer-weeks for the adapter layer,
plus another week for environment, identity, and deployment verification, and a final pass for performance and
cost tuning. That is not a huge amount, but it is not free either. In this case, the abstraction was useful for
keeping the data path and model-serving interfaces out of application code, especially for the pipeline and
model-management logic. But it was not magic: the provider-specific response shape and deployment model still
leak, which is why I would treat the adapter as a disciplined seam rather than a promise of full portability.
Honest verdict: the abstraction was worth it for the training and data path, but I would not pretend it removes
all platform-specific operational work.
